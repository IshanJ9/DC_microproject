A cache that keeps working when a server dies

FlashMart is a shop backed by a real database, with a distributed cache in front of it. Several cache servers share the work using consistent hashing, answer over gRPC, and keep a spare copy of every item.

How it works

  1. Without a cache, every page waits

    Each product page asks the database. It takes about 180 ms and gets slower the more people arrive at once.

  2. Every key gets a spot on a ring

    A product's key is hashed to a point on a circle. The first server clockwise from that point owns it.

  3. The next server holds a spare copy

    If the owner stops answering, reads go to the replica. Shoppers never see an error.

  4. Servers can join or leave

    Only the keys next to the change move. Plain hash(key) % N would reshuffle most of them.

Concepts this project covers

  • Remote procedure calls Nodes expose Get, Put, Delete, Ping and more over gRPC.
  • Partitioning Consistent hashing with virtual nodes spreads keys evenly.
  • Replication Each key lives on two servers.
  • Failure detection Two missed heartbeats mark a server down.
  • Fault tolerance Reads fail over to the replica during the gap.
  • Rebalancing Joins and failures move only the affected keys.

    products table

    How a read works

    1. Ask the key's owner server (then its replica) for the row.
    2. Found: return it. This is a cache hit.
    3. Not found: run SELECT on the database, return the row, and store a copy on both servers.

    Use Read on a row. Read it twice: first from the database, then from the cache.
